# Database Recovery Systems & The ARIES Algorithm

This document details failure classification models, Write-Ahead Logging (WAL), Checkpointing protocols, and the industry-standard ARIES recovery algorithm.
Maps directly to **CSE3001 Unit 5**.

---

## 1. Failure Classification

1. **Transaction Failure**:
   - Logical errors (e.g. business rule violation, division by zero).
   - System error (e.g. deadlock detection victim abort).
2. **System Crash (Soft Failure)**:
   - Power outage, OS kernel panic, DBMS process crash.
   - Volatile memory (RAM Buffer Pool) is wiped out; Non-volatile disk data remains intact.
3. **Media / Disk Failure (Hard Failure)**:
   - Physical disk head crash, corrupted sectors.
   - Recovered via RAID redundancy + Hot/Cold archive backups (`scripts/backup_restore.sh`).

---

## 2. Write-Ahead Logging (WAL) Protocol

### Core WAL Invariants:
1. **Rule 1 (Undo Rule)**: Before a dirty data page in RAM can be written to disk, the log record containing the before-image ($V_{\text{old}}$) must be flushed to disk. *(Enables rollback/atomicity)*.
2. **Rule 2 (Redo Rule)**: Before a transaction is marked as committed, all log records generated by the transaction (up to the commit record) must be flushed to non-volatile disk. *(Enables durability)*.

### Log Record Structure:
Each log record has a unique monotonically increasing **Log Sequence Number (LSN)**:
$$\langle \text{LSN}, \text{PrevLSN}, \text{TransID}, \text{Type}, \text{PageID}, \text{Offset}, V_{\text{old}}, V_{\text{new}} \rangle$$

---

## 3. The ARIES Recovery Algorithm

ARIES (Algorithms for Recovery and Isolation Exploiting Semantics) executes in 3 distinct sequential phases upon restart after a system crash:

```
          [ Crash Event ]
                 │
                 ▼
  ┌──────────────────────────────┐
  │   PHASE 1: ANALYSIS PHASE    │  Determines Dirty Page Table (DPT) & Loser Transactions
  └──────────────┬───────────────┘
                 │
                 ▼
  ┌──────────────────────────────┐
  │     PHASE 2: REDO PHASE      │  "Repeats History" - Reapplies all updates from min(RecLSN)
  └──────────────┬───────────────┘
                 │
                 ▼
  ┌──────────────────────────────┐
  │     PHASE 3: UNDO PHASE      │  Rolls back all uncommitted Loser Transactions (writes CLRs)
  └──────────────┬───────────────┘
                 │
                 ▼
      [ Normal DBMS Operation ]
```

### 3.1 Phase 1: Analysis Phase
- Starts scanning the WAL log forward from the most recent **Fuzzy Checkpoint**.
- Reconstructs two essential memory tables:
  1. **Transaction Table (TT)**: Tracks all active transactions at crash time (**Losers**).
  2. **Dirty Page Table (DPT)**: Tracks pages modified in RAM but not yet flushed to disk, recording their `RecLSN` (the earliest LSN that dirtied the page).

### 3.2 Phase 2: Redo Phase ("Repeating History")
- Finds the smallest `RecLSN` across all pages in the DPT.
- Scans forward through the log from $\min(\text{RecLSN})$ to the end of the log.
- Re-executes every logged operation (including actions of failed/loser transactions) unless the page on disk already has $\text{PageLSN} \ge \text{LogLSN}$.
- **Result**: Restores database state to the exact millisecond before the crash.

### 3.3 Phase 3: Undo Phase ("Rolling Back Losers")
- Scans the log backward starting from the largest LSN of all loser transactions.
- Undoes every update made by loser transactions.
- For every undone action, writes a **Compensation Log Record (CLR)**:
  - CLRs are *never undone* during subsequent crashes, preventing infinite recovery loops.
- Writes an $\langle \text{END} \rangle$ record for each loser transaction once fully rolled back.
